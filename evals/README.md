# Eval datasets

LangSmith datasets for this agent. One JSONL file per component / topic, **20 examples each**, and
every line has exactly two keys: `inputs_1` (the input) and `outputs_1` (the reference output).
Anything that needs a second label lives in its own file rather than an extra column.

## Component datasets

| File | Component under test | `outputs_1` |
| --- | --- | --- |
| `guard_routing.jsonl` | `guard_scope` + `route_after_guard`, in-scope classification | `wallet` / `transaction` / `knowledge` |
| `guard_scope_boundary.jsonl` | `guard_scope` refusal behaviour: 15 out-of-scope + 5 over-refusal traps | `refuse` or the correct in-scope route |
| `guard_protocol.jsonl` | `guard_scope`'s `protocol` field (steers retrieval filtering) | `lifi` / `morpho` / `both` / `none` |
| `extract_wallet.jsonl` | `extract_wallet` regex extraction | the address or ENS name, or `none` |
| `extract_tx.jsonl` | `extract_tx` regex extraction | the 66-char hash, or `none` |
| `query_rewrite.jsonl` | `_rewrite_query` on multi-turn follow-ups | the expected standalone query |
| `tool_selection_wallet.jsonl` | `wallet_agent` first-turn tool choice | required tool names, comma-separated |
| `tool_selection_tx.jsonl` | `tx_agent` first-turn tool choice | required tool names, comma-separated |

Notes:

- **Route, not raw fields.** The two `guard_*` routing files grade the decision the way
  `route_after_guard` computes it: `refuse` when `in_scope` is false, otherwise `intent`. Protocol is
  graded separately in `guard_protocol.jsonl` — a wrong protocol only narrows retrieval, so it is a
  softer failure than a wrong route.
- **Over-refusal matters.** `guard_scope_boundary.jsonl` is deliberately not all-`refuse`; its last five
  rows are in-scope questions a too-strict guard rejects. A guard that refuses everything scores 75%
  on that file and 0/5 on the traps, which is the signal you want.
- **Extraction is pure regex.** Every label was generated by running the real `ADDRESS_RE` / `ENS_RE` /
  `TX_HASH_RE` over the input, so the target should be the regex match, *before*
  `resolve_ens_address` and before the `state.address` / `connected_address` fallback (both need live
  state or network). `none` means no match, i.e. the graph must reach the clarify interrupt.
  Coverage includes checksummed and lowercase addresses, a 64-hex hash that must **not** match as an
  address, over- and under-length hex, a missing `0x`, an ENS subdomain, two candidates in one
  message, backticks/URLs, and CJK text.
- **Two rows pin current behaviour that is arguably a bug** — if the regexes are fixed, update them:
  - `extract_wallet.jsonl`: `VITALIK.ETH holdings` → `none`, because `ENS_RE` only matches a lowercase
    `.eth` suffix, though ENS names are case-insensitive.
  - `extract_tx.jsonl`: a 65-hex string → the first 64 characters. `TX_HASH_RE` has no trailing
    negative lookahead, so unlike `ADDRESS_RE` it silently truncates instead of rejecting.
- **Rewrite is judged, not matched.** Use an LLM judge for semantic equivalence: the rewrite must
  resolve the pronoun or ellipsis and keep the user's key terms without inventing new topics.
  `_rewrite_query` returns the raw question on the first turn, so every row here is multi-turn.
- **Tool selection grades the first assistant turn.** Invoke `wallet_agent` / `tx_agent` once and check
  `required ⊆ called`, not set equality — `WALLET_SYSTEM` legitimately tells the agent to fetch both
  positions and balance, so a superset is fine. Worth asserting separately: on any row whose input
  already contains a literal `0x` address, `resolve_ens` should **not** be called.

## Knowledge (RAG) datasets

`inputs_1` question → `outputs_1` reference answer, written from the vendored corpus in `docs/`, so they
work as ground truth for correctness / groundedness judges.

| File | Topic | Source pages |
| --- | --- | --- |
| `lifi_routing_quotes.jsonl` | What LI.FI is, product stack, quote vs route, slippage & price impact, intents, security | `docs/lifi/introduction-*`, `faqs-slippage-price-impact` |
| `lifi_status_troubleshooting.jsonl` | `/status` statuses & substatuses, error codes, debugging reverted transactions | `docs/lifi/…status-tracking`, `faqs-route-availability`, `guides-debug-failed-transactions` |
| `morpho_markets_rates.jsonl` | Market structure & the five parameters, LLTV set, AdaptiveCurveIRM, APY formulas, assets vs shares, interest accrual | `docs/morpho/learn-concepts-blue`, `learn-concepts-irm`, `developers-borrow-concepts-interest-rates`, `…market-mechanics` |
| `morpho_risk_liquidation.jsonl` | LTV & health factor, liquidation and LIF, bad debt, oracles, protocol risks | `docs/morpho/…ltv`, `learn-concepts-liquidation`, `developers-borrow-concepts-liquidation`, `learn-concepts-oracle`, `learn-resources-risks` |
| `morpho_vaults.jsonl` | Vault V2 adapters, ID/cap system, roles, timelocks, fees, ERC4626, inflation protection, loss socialization | `docs/morpho/learn-concepts-vault-v2`, `developers-earn-concepts-vault-mechanics` |

Splitting by source page is deliberate: a low score on one file points at the chunking/retrieval of
those specific pages rather than at the RAG chain as a whole. Three rows are arithmetic checks (LTV /
health factor, a liquidation payout) to catch answers that read well but are numerically wrong.

## Upload

UI: Datasets → New dataset → upload the `.jsonl`; `inputs_1` becomes the input and `outputs_1` the
reference output.
SDK: `client.create_dataset(...)` + `client.create_examples(inputs=[...], outputs=[...])`.

The existing `scripts/eval_routing.py` (`make eval`) covers a subset of `guard_routing` +
`guard_scope_boundary` locally, without LangSmith.
